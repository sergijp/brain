# Trading Rules v2.0 — Mandatory Workflow

> **Призначення**: набір обов'язкових правил для будь-якого Top-Down Analysis (TDA) та виконання угод.
> **Джерело**: дистильовано з Daily Retros 2026-04-23 (+11.1R) та 2026-04-24 (−3R, 3 INVALID плани).
> **Hard rule**: всі правила застосовуються до кожного інструмента, без винятків.

---

## 🟥 Правило 0 — INTRADAY ONLY (FOUNDATIONAL)

**Ми торгуємо ТІЛЬКИ інтрадей. Позицій overnight/swing немає.**

### Жорсткі обмеження:
- ✅ **Усі позиції відкриваються та закриваються в межах одного торгового дня (00:00 → 23:59 UTC)**
- ❌ **НЕ переносити позицію через ніч** (close → next day open)
- ❌ **НЕ переносити через вікенд** (Friday close → Monday open)
- ⏰ **Hard close time:**
  - Forex/Metals: **до 19:00 UTC = 22:00 Київ** (оновлено 2026-08-24, було 21:00 UTC)
  - Indices (US100/US500/GER40): до 20:00 UTC
  - П'ятниця: примусове закриття до 19:00 UTC незалежно від P&L

### TP не досягнуто до closing time:
```
if current_time >= hard_close and position.is_open:
    market_close(position)
    log("Forced intraday close — TP not reached")
```
- Не «давати трейду шанс ще день»
- Не «трохи подовжимо, бо MFE великий»
- Закрити по ринку — без винятків

### Ситуація «немає позиції»

**Якщо немає відкритої позиції на даний момент — ОБОВ'ЯЗКОВО так і казати!**

Заборонено:
- ❌ Вигадувати позицію якої немає
- ❌ Описувати «гіпотетичну позицію» як реальну
- ❌ Казати «у нас Long на EURUSD» якщо нічого не відкривали
- ❌ Робити аналіз так, ніби позиція вже існує

Обов'язково:
- ✅ «Зараз позицій НЕМАЄ. Виконую аналіз для пошуку setup.»
- ✅ «Угод сьогодні не відкривали. Trade plan готовий, чекаємо тригер.»
- ✅ Якщо ретро/підсумок — чесно вказувати «entry не тригернувся, угоди не було»
- ✅ Розрізняти **plan** (рівні готові, чекаємо) vs **active position** (відкрита) vs **closed** (зафіксована)

### Перевірка перед розмовою про P&L:
```python
# Auto-check before any P&L statement
positions = check_open_positions()  # via replay_trade status or manual log
if not positions:
    say_explicitly("Відкритих позицій НЕМАЄ")
    do_not_fabricate_pnl()
```

**Чому це Правило 0:**
- Інтрадей-стратегія SMC + PA Combo побудована саме на сесійних рухах (London/NY KZ), не на тижневих трендах
- Overnight risk = неконтрольовані гепи, news, азійські маніпуляції
- Капітал $10,000 з ризиком 1% не витримує overnight волатильність indices/metals
- Чітке розділення «є позиція / немає позиції» — основа дисципліни та чесної звітності

## 🟥 Правило 1 — Pre-Flight Price Verification (АВТОМАТИЧНЕ)

**ПЕРЕД** написанням TDA для кожного інструмента — обов'язковий MCP виклик:

```python
# Auto-executed by Claude before generating any analysis
quote = mcp__tradingview__quote_get(symbol)
current_price = quote.last

# Hard validation
if abs(planned_entry - current_price) / current_price > 0.05:  # 5% threshold
    raise ABORT_PLAN(f"Scale error: entry {planned_entry} vs current {current_price}")
```

**Workflow integration:**
1. Перед `chart_set_symbol` → виклик `quote_get` для current price
2. Записати current_price у frontmatter analysis-файлу: `current_price_at_analysis: X.XXXX`
3. Усі рівні (entry/SL/TP) — **в межах ±5% від current_price**
4. Якщо план уже згенеровано і перевищує threshold → **видалити та регенерувати**

**Чому це блокувальне правило:**
- 2026-04-24: 3/10 планів (USDCHF/XAGUSD/US500) мали entry на хибному масштабі (1000+ pips off)
- Workflow генерування на основі screenshots без верифікації → systematic failure

**Винятки:** немає.

## 🟥 Правило 2 — BE@2R Mandatory + TradingView Alert

**Відразу після відкриття позиції** (через `replay_trade` або реальне виконання):

```python
# Calculate BE level (2R from entry)
be_level = entry + 2 * (entry - sl)  # for LONG
# or: be_level = entry - 2 * (sl - entry)  # for SHORT

# Auto-create alert
mcp__tradingview__alert_create(
    symbol=symbol,
    price=be_level,
    message=f"BE@2R for {symbol} — move SL to entry NOW",
    condition="crosses"
)
```

**При спрацюванні alert:**
- SL → BE (entry price) безумовно
- НЕ обговорюємо, не аналізуємо «чи варто», просто переносимо

**Партійна фіксація:**
- MFE = 1:2 → SL→BE
- MFE = 1:3 → fix 30% позиції
- MFE = 1:4+ → fix 50%, runner на 1:5+

**Чому це блокувальне правило:**
- GER40 04-23: MFE 7.47R → SL hit → −1R замість +3R+
- GER40 04-24: MFE 5.78R → SL hit → −1R замість +2.5R+
- 2 дні поспіль той самий інструмент → **~5-7R втрачено**
- Правило існувало, але виконувалось «вручну» = не виконувалось

**Винятки:** немає.

## 🟧 Правило 3 — Bias Re-validation на NY Open (13:55 UTC)

**Тригер:** автоматичний alert на 13:55 UTC (5 хв до NY open).

**Checklist re-validation:**
```
1. chart_set_timeframe("60") + chart_get_state()
2. Перевірити структуру H1 vs ранковий bias:
   - Bias був Bullish? → Перевірити чи немає LH (lower high) проти bias
   - Bias був Bearish? → Перевірити чи немає HL (higher low) проти bias
3. quote_get("DXY") — порівняти з ранковим напрямком
4. Якщо ChoCH/MSS проти bias на H1 → анулювати pending orders
```

**Дії за результатами:**
| Стан | Дія |
|------|-----|
| Bias підтверджено | Continue з планом |
| H1 structure broken | Cancel pending orders, спостерігати |
| DXY reversed | Re-run TDA для USD-pairs |
| Already in position | Tighten SL до BE або partial close 50% |

**Чому це правило:**
- 2026-04-24: 6 з 7 валідних позицій змінили долю саме о 14:00 UTC
- 2026-04-23: NY open також був точкою реверсу для US500
- 2026-04-22: те саме (London Lunch reversal)
- **Третій день поспіль** — це не випадковість, це pattern

**Тригер:** перед London open (06:00 UTC) — додатковий перевірочний сканер.

**Logic:**
```python
yesterday_retro = read_daily_retro(today - 1)
trend_day = (yesterday_retro.tp_hit_count >= 3 
             and yesterday_retro.usd_direction in ["strong", "weak"])

if trend_day:
    # Run reversal detection
    for symbol in watchlist:
        chart_set_timeframe("60")
        check_choch_against_yesterday_bias()
        if choch_detected:
            mark_for_bias_flip(symbol)
```

**Дії:**
- Якщо вчора був trend day (3+ TP_HIT в одну сторону USD):
  - **НЕ екстраполювати** автоматично сьогоднішні плани
  - Зранку додатковий H1 check на 50% watchlist

- Якщо вчора був mixed/loss day → стандартний workflow

**Чому це правило:**

## 🟨 Правило 5 — Entry Layer 3 (Continuation/Breakout)

Окрім традиційних 2 entries (aggressive OTE 70%, safe OTE 61%) — **обов'язковий третій layer**:

**Continuation entry** активується коли:
- На open ціна вже за межами OTE зони (>50 pips від aggressive entry для FX, >100 pts для indices)
- HTF bias підтверджений
- Local M15 ChoCH у напрямку bias

**Setup:**
```
Entry = breakout локального H/L поточного дня + 5 pips
SL = за останній M15 swing (зазвичай 20-40 pips)
TP1 = 1:2 RR
TP2 = HTF target (як у safe entry)
Розмір: 0.5× стандартного (бо tight SL)
```

**Чому це правило:**
- 2026-04-24 US100: entry 26780, day low 26876 → entry never triggered, +357 pts втрачено
- 2026-04-23 ще декілька кейсів того ж типу

# 🚨 Анти-патерни бектесту (додано 2026-08-24)

Витягнуто з провалених валідацій ТС-1/ТС-3 і з дослідження 962 стратегій. Кожен пункт коштував реального циклу роботи — перечитувати **перед** тим, як оголошувати стратегію робочою.

## A1. Едж може бути реальним і при цьому меншим за спред

**ТС-1:** PF **1.135** при нульових витратах → PF **0.79** після реальних FX-костів. Перехід на H1 не врятував.

> Бектест без витрат не відповідає на питання «чи є едж» — він відповідає на питання «чи є едж, більший за нуль». Це різні питання.

**Правило:** витрати рахувати **симетрично** — `RR = (target − cost) / (SL + cost)`. Варіант «витрати лише переможцю» заборонений.

**Похідне:** чим тісніший SL, тим вища чутливість до моделі витрат. При `cost/SL > 25%` результат визначається радше моделлю витрат, ніж стратегією.

## A2. Прибутковість на одній парі може бути прихованим напрямком

**ТС-3:** EURUSD PF 1.43 → GBPUSD PF **0.39** (WR 19%). Діагноз: *shorts-only FVG = прихований trend-follower*, який працює лише поки пара падає.

> Якщо стратегія односпрямована (тільки шорти / тільки лонги), спершу перевір, чи не міряєш ти напрямок ринку замість патерну.

**Тест:** додати дзеркальну сторону. Якщо результат вирівнюється — це був патерн. Якщо обвалюється — це був тренд.

⚠️ **Але:** cross-pair провал доводить лише **неуніверсальність**. Для однопарного трейдера це не є підставою відкидати стратегію — це підстава перевірити її **на своїй парі окремо**.

## A3. Knife-edge параметри

Ознака: невелика зміна порога різко міняє результат, а «монотонність гріда» тримається на 2-3 конкретних угодах.

Приклади з дослідження 962:
- №88 `asia_range 15–35п` — на січні-лютому обвалив результат з −10.1 до **−61.5п**
- №534 `head-break <= 5.0п` — на січні-лютому гірше на **73п**

**Правило:** будь-який фільтр перевіряти на вікні, на якому він **не** підбирався. Не пройшов — відхилити, навіть якщо на DEV красиво.

## A4. Gate-shopping

Якщо ціль A не проходить RR-гейт, і ти береш ціль B **тому що вона проходить** — це підгін, а не вибір.

> Вибір між варіантами цілі робиться **до** угоди і за статистикою, а не під конкретний сетап.

## A5. Метод тестування може провалити стратегію, якої не тестував

**ТС-2:** Pine дав 11 угод, WR 0-9%, gross $0. Реальний висновок — **Pine не годиться як proxy для дискреційного еджу**, а не «стратегія не працює».

**Правило:** перш ніж записувати FAIL, спитати — чи інструмент узагалі здатен виміряти те, що я міряю?

## A6. Протокол валідації (єдиний чинний)

```
DEV        — налаштування дозволене
CHECKPOINT — проміжна перевірка, налаштування ЗАБОРОНЕНЕ
ГЕЙТ       — сліпе вікно, недоторкане до фінального прогону
```

Чесний симулятор без lookahead: `~/AI/research/strategies/s88/sim.py`, `s534/simlib.py`.
**Pine як бектест-proxy більше не використовується.**

Стратегія вважається валідованою, лише якщо результат тримається на **всіх трьох** вікнах. Провалений CHECKPOINT при пройденому ГЕЙТі (як у [[quasimodo-534]]) — це **режимна залежність**, і її треба назвати явно, а не усереднити.

## A7. Нульова модель — обов'язковий тест (додано 2026-08-24)

**Перш ніж вважати стратегію прибутковою, треба знати, скільки дає випадковий вхід у тих самих умовах.**

Без цього числа `+279 пунктів` не означає нічого — невідомо, це едж чи просто дрейф ринку.

### Як будувати

Вичерпний перебір: вхід на **кожному** допустимому барі (той самий часовий фільтр, ті самі дні), обидва напрямки, **той самий ризик і та сама механіка виходу**, що в стратегії.

Приклад для EURUSD M15, 7–18 UTC, будні, risk 19.5п, TP 1.5R, flat 19:00:
```
НУЛЬ:  15 168 входів  →  WR 41.8%,  −1.47п/угоду
                          ↑ рівно спред + 2×сліпедж
```

### Що з цим робити

| Метрика | Сенс |
|---|---|
| **Надлишок над нулем** | `сер_стратегії − сер_нуля` для тих самих годин і напрямків. Це і є едж |
| Нуль по годинах | Якщо якась година додатна на нулі — часовий ефект існує і його треба відняти |
| Нуль по напрямках | Асиметрія long/short на нулі = дрейф ринку, а **не** едж стратегії |

⚠️ **Асиметрія напрямку на нулі — типова пастка.** У 2026 EURUSD дрейфував униз, тому нуль давав short −0.22п, long −2.63п. Стратегія з перекосом у шорти виглядала б прибутковою, не маючи еджу взагалі.

### A8. Тест «без топ-N»

**Якщо видалення 10 найкращих угод із 71 робить результат гіршим за нуль — едж не існує, є десять везучих угод.**

Приклади:
- №534 QM: пул +168.8п → **без топ-10: −168.0п** на решті 61 угоди (гірше за нуль)
- BnR (372 угоди): +277.3п → **без топ-10: −187.5п**

Дивитись треба на **медіанну угоду**. Якщо вона від'ємна, а total додатний — увесь результат у хвості.

### A9. Перевірка стійкості до параметра вікна

Зміна одного параметра на сусіднє значення **не має перевертати знак**.

`look` 60 → 90 барів у BnR: **+277п → −144п**. Це не стратегія з параметром, це шум із зафіксованим числом.

Так само `buf` SL 2/3/5п дав +112 / +277 / +437 — монотонність тут означає «ширший стоп менше вибиває», а не наявність еджу.

# 🧮 A10. Закон витратного дрейфу (доведено емпірично 2026-08-24)

**Випадковий вхід із фіксованим SL і TP дає expectancy:**

```
E_нуля  ≈  − c / (SL + c)          де c = 2.0 п для EURUSD
                                    (спред 1.0 + сліп 0.5 вхід + 0.5 вихід)
```

> ⚠️ **Уточнено 2026-08-24 (вечір).** Спершу використовувалось `c = 1.5` — це занижувало поріг на ~20% при малих SL. Емпірична медіана `c_eff` по 21 клітинці = **1.978**.

## 🔑 Найважливіше: таймфрейм — НЕ змінна

| SL, п | M15 | H1 | H4 |
|---|---|---|---|
| 15 | −0.111 | −0.105 | −0.112 |
| 40 | −0.047 | −0.047 | −0.048 |
| 90 | −0.022 | −0.022 | −0.022 |

**Ідентично до третього знака.** У формулі немає ТФ — тільки розмір стопа.

«Перевага вищого таймфрейму» — ілюзія: вона зводиться до того, що там зазвичай ставлять ширший стоп. Той самий ефект дає ширший стоп на M15.

Виміряно на чотирьох незалежних вікнах EURUSD (2024-2026), стабільно **до третього знака**:

| SL, п | 5 | 8 | 12 | 18 | 24 | 32 | 45 |
|---|---|---|---|---|---|---|---|
| E нуля | −0.31 | −0.20 | −0.14 | −0.09 | −0.07 | −0.06 | −0.04 |

## Три наслідки, які змінюють підхід до розробки

### 1. Тісний стоп — це дорожче, а не дешевше

Скорочення SL з 22п до 9п **потроює** витратний дрейф: −0.06R → −0.19R на угоду.

Інтуїція «тісніший стоп = кращий RR = краще» **хибна**: приріст RR у пунктах точно компенсується падінням winrate, а частка витрат на одиницю ризику зростає.

### 2. RR і winrate — одна величина у двох записах

Будь-яке перетасування точки входу/виходу рухає їх **дзеркально**, лишаючи E на `−cost/(SL+cost)`.

> Геометрія не створює едж. Вона його лише перерозподіляє між WR і RR.

**Перевірено на №88:** три конструкції входу підняли `RR_net` з 0.43 до 1.0–1.8 — expectancy не покращилась на жодному вікні.

### 3. Високий winrate може бути артефактом геометрії

Нульова модель із геометрією №88 (`SL ≈ 0.94×range`, `TP ≈ 0.51×range`) сама дає **WR 60-61%** — без жодного сигналу.

Спостережений winrate 65-75% виглядав як доказ якості. Насправді це просто стоп, удвічі довший за ціль.

> **Перш ніж радіти winrate — порахуй, який WR дає монетка з тією ж геометрією.**

## Що з цього випливає для розробки

**Єдине джерело еджу — прогноз напрямку.** Не розташування стопа, не вибір цілі, не час виходу.

Правильне перше питання до будь-якої ідеї:

> Чи б'є мій сигнал **монетку на тих самих барах**?

Якщо ні — жодна оптимізація геометрії не допоможе, бо оптимізується розподіл між WR і RR, а не їхній добуток.

## Історія: чому це коштувало трьох стратегій

| Стратегія | Що робила | Результат на невидимих даних |
|---|---|---|
| ASR+ORB | sweep + reclaim + фільтри F1-F5 | E −0.373 (DEV), N=0 за 74 дні форварду |
| №534 QM | 4-півотна структура + BOS + ретест | надлишок над нулем −5.50R на CHECKPOINT |
| №88 | Asia sweep + CHoCH reclaim | надлишок над нулем **−0.001R** на 100 угодах |

**Усі три — геометричні перетасування без напрямкового прогнозу.** Жодна не намагалась передбачити напрямок; усі переставляли стопи й цілі навколо випадкового блукання.

Нульова модель коштує хвилини і відсіяла б усі три **до** тюнінгу. Інструмент: `~/AI/research/strategies/s88/entry_v2.py` — функції `null_matched`, `null_exhaustive`, таблиця `E(S)`.

# 🎭 A11. Тест дубльованої ознаки — як викрити «стабільний знак»

**Проблема:** ознака показує однаковий знак ефекту на всіх вікнах. Виглядає як доказ стійкості. Насправді може бути стабільністю монетки, яку один раз підкинули.

## Прийом

Візьми **ту саму ознаку у двох нормуваннях** (напр. «тіло свічки в пунктах» і «тіло свічки / ATR») і прогони обидві незалежно.

- Якщо ознака має реальний сигнал — обидві версії дадуть **однаковий** знак
- Якщо це шум — вони дадуть **дзеркально протилежний** знак, і кожна виглядатиме «стабільною»

## Реальний випадок (2026-08-24, тест 24 ознак на 454 sweep-подіях)

```
B_prevday_body_p    (тіло у пунктах):  −.019  −.012  −.051  −.033
C_prevday_body_atr  (тіло / ATR):      +.019  +.012  +.061  +.043
```

Обидві — тіло попередньої денної свічки. |r| на discovery ≈ 0.01. Знак було обрано випадково при навчанні, і далі кожна версія «стабільно» відтворювала свій випадковий знак на всіх чотирьох вікнах.

**Без цього тесту `C` виглядала б як найкраща знахідка дослідження.**

# 🎯 A12. Арифметика беззбитковості для напрямкового сигналу

Перш ніж радіти accuracy — порахуй, скільки її треба:

```
p* = 0.5 + cost / (2 × M)
```
де `M` — медіанний розмір руху, який ловиш.

| M | p* при cost 1.5п |
|---|---|
| 10п | 0.575 |
| 15п | 0.550 |
| 22п | 0.534 |
| 50п | 0.515 |
| 100п | 0.508 |

**Два наслідки:**

1. **Чим менший рух — тим вища потрібна точність.** На M15 з рухом 10-20п треба 55-57% — це рівень, недосяжний для роздрібних технічних ознак.
2. **Дивись на нижню межу CI, не на point estimate.** Accuracy 0.550 з CI [0.491; 0.607] при порозі 0.532 не означає нічого: поріг усередині інтервалу, нижня межа нижча за монетку.

> Зв'язок з [[#A10]]: обидві формули кажуть те саме з різних боків — витрати фіксовані, тому все, що ловить малі рухи, вимагає нереалістичної точності.

# ⚖️ A13. Пастка вищого таймфрейму (виміряно 2026-08-24)

Спокуслива логіка: «витратний дрейф падає з розміром стопа → перейду на H4 → едж вижене».

**Виміряно на трьох механіках × трьох ТФ × двох режимах утримання (18 комбінацій, 4 вікна):**

| Механіка | M15 | H1 | H4 |
|---|---|---|---|
| E (mean reversion) | −0.174 | −0.118 | **−0.028** |
| E нуля | −0.147 | −0.081 | **−0.034** |
| **Надлишок** | −0.027 | −0.037 | **+0.006** |

Абсолютна expectancy справді покращується втричі — **і зупиняється рівно на нулі моделі**.

Надлишок по всіх 18 комбінаціях: середнє **−0.014R**, жоден CI не виключає нуля.

## Механізм

> Ширший стоп рятує від витрат — **і водночас розмиває сигнал**. Ті самі 3п шуму, що вбивали 15-пунктовий стоп, не заважають 56-пунктовому. Але й інформація, яку ніс 15-пунктовий рівень, у 56-пунктовому вікні вже не має значення.

Два ефекти компенсуються. Це не збіг — це те саме, що каже A10: у формулі `E_нуля` немає нічого, крім `c` і `SL`.

## Два практичні наслідки

### 1. H4-геометрія несумісна з інтрадей-flat

| Механіка (SL 56п) | flat 22:00 Київ | утримання до 5 діб |
|---|---|---|
| range breakout H4 | **forced_close 87%** | TP 44% / SL 40% |
| mean reversion H4 | **forced_close 90%** | TP 38% / SL 45% |

Дев'ять із десяти угод закриваються **за годинником, а не за планом**. План перестає бути планом.

При `SL ≤ 25п` обмеження терпиме (forced_close 8–31%).

### 2. Вищий ТФ так само вповільнює перевірку

| ТФ | Поріг для виміру | Похибка на 22 міс | n потрібно | Років на 1 парі |
|---|---|---|---|---|
| M15 | 0.118 | ±0.098 | 209 | 1.3 |
| H1 | 0.076 | ±0.101 | 468 | 3.3 |
| **H4** | **0.036** | **±0.060** | **632** | **5.3** |

**На H4 роздільна здатність гірша за поріг, який треба виміряти.** Реальний край +0.04R там просто не видно.

> Вищий ТФ знижує поріг прибутковості — і **рівно настільки ж** уповільнює його перевірку. Виграшу немає.

## Що з цього випливає

Якщо повертатись до вищих ТФ — то **не з довшою історією однієї пари**, а з **портфелем із 10-20 інструментів паралельно**. Тільки так набирається `n` за розумний час.

Це вже інша архітектура — і збігається з тим, що каже література: задокументований едж живе у крос-секційних кошиках з місячним ребалансуванням (Sharpe 0.8–1.0), а не в одній парі на інтрадеї.

# 🔬 A14. Брак потужності ≠ відсутність ефекту (додано 2026-08-25)

## Помилка, яку робили ми самі

Звіт по 24 напрямкових ознаках на 454 sweep-подіях був сформульований як **«жодна ознака не б'є монетку»**. Це неправда — точніше, це твердження, якого ті дані не могли підтвердити.

При `n = 454` мінімальний ефект, який виявляється з потужністю 80% при α=0.05:

```
d_min = 2.80 / √n = 2.80 / √454 = 0.131R          (без поправки)
d_min = 3.92 / √n = 3.92 / √454 = 0.184R          (Bonferroni на 24 тести)
```

Едж **0.05–0.10R** — цілком робочий для механічної системи — на такій вибірці не видно **в принципі**.

Правильне формулювання результату: *«едж більший за 0.18R виключено; менший — не перевірено»*.

## Скільки треба спостережень

| Едж | 1 тест | Bonferroni на 24 |
|---|---|---|
| 0.05R | ~3 140 | ~6 160 |
| 0.10R | ~785 | ~1 540 |
| 0.15R | ~350 | ~685 |

Формула: `n = ((z_{α/2} + z_β) / d)²`, при 80% потужності чисельник = 2.80 (або 3.92 з поправкою).

## Правило

**Перед висновком «ефекту немає» — рахувати `d_min` для наявного `n`.** Якщо шуканий ефект менший за `d_min`, коректний висновок один: *вибірки не вистачає*. Писати «сигналу немає» заборонено.

`lib/feature_lab.py::power_check()` рахує це автоматично — викликати обов'язково, разом з `evaluate_feature`.

## Практичний наслідок для вибору стратегії

При **5–6 угодах/міс на одній парі** набрати 3 000 угод = **43 роки**. Тому пріоритет мають гіпотези з **високою частотою подій** (щоденні часові вікна дають ~500 подій/рік проти ~60 у сетапного патерну) — не тому, що вони перспективніші, а тому що їх узагалі **можливо перевірити за життя**.

> Зв'язок з [[#A13]]: там ішлося про те, що вищий ТФ уповільнює перевірку. Тут — та сама арифметика з боку частоти сигналу.

# 🧾 A15. Результат без відтворюваних даних не є результатом (додано 2026-08-25)

## Випадок

Картка [[liquidity-sweep-88]] стверджувала: **«ГЕЙТ (вер–гру 2025, сліпі дані): n=30, WR 70.0%, +44.4п, PF 1.31»**. На цій цифрі трималися: статус `validated`, expectancy-гейт у `risk-rules.md` і дозвіл торгувати з `RR ≤ 1.0`.

Аудит 25.08 показав: **у `data/` немає жодного файлу за вересень–грудень 2025.** Прогін того самого коду на наявних сліпих вікнах дав `−40.7п`, `PF 0.93` — протилежний знак при схожому winrate.

Причина, найімовірніше, невинна: `data/` втрачено разом зі scratchpad і перезавантажено через replay. Але наслідок від цього не менший — **живі торгові дозволи спиралися на число, яке ніхто не міг перерахувати.**

## Правило

Результат, що дає стратегії статус, зобов'язаний бути **відтворюваним однією командою на файлах, які лежать у репозиторії зараз**.

| Вимога | Перевірка |
|---|---|
| Файли даних наявні | період з картки покривається реальним CSV — звіряти `head`/`tail`, не назву файлу |
| Команда збережена | у картці вказано скрипт і аргументи, якими число отримано |
| Число сходиться | перерахунок дає той самий знак і порядок |
| Константи ті самі | `COST`, `FLATTEN_HOUR` на момент прогону — зафіксовані в картці |

**Не сходиться хоча б одне → статус знімається до перерахунку.** Не «уточнюється», не «позначається зіркою» — знімається.

## Похідне: константи мають одне джерело

Той самий аудит знайшов `COST = 2.0` в одному файлі та `COST = 1.5` ще у трьох, і три різні значення flat-часу в межах одного проєкту (17:45 Київ / 19:00 UTC / 21:00 UTC).

**Перед прогоном, що змінює статус стратегії — `grep` по константах через усю кодову базу.** Розбіжність = результати непорівнянні, навіть якщо кожен окремо порахований правильно.

> Зв'язок з [[#A6]]: протокол валідації описує, **як** міряти. A15 вимагає, щоб виміряне можна було **перевіряти повторно**.

# 🪟 A16. Вікно вимірності — де взагалі може жити механічний едж (додано 2026-08-25)

## Дві стіни, між якими треба поміститись

Механічна стратегія затиснута між двома обмеженнями, що діють у **протилежних** напрямках.

**Стіна витрат.** Едж на угоду має бути суттєво більшим за `c = 2.0` п. Щоб витрати з'їдали не більше 20%, потрібно:

```
едж ≥ 5 × c = 10 пунктів на угоду
```

**Стіна потужності** ([[#A14]]). Едж треба ще й **виміряти**. При `sd` угоди ≈ 31 п:

| Едж | у частках sd | `n` для 80% потужності |
|---|---|---|
| 1 п | 0.032 | ~7 600 |
| 3 п | 0.097 | ~830 |
| **10 п** | **0.32** | **~77** |
| 20 п | 0.65 | ~19 |

## Вікно

```
        едж < 10п              едж ≥ 10п
   ┌──────────────────┐   ┌──────────────────┐
   │ спостережень     │   │ ВІКНО            │
   │ вистачає, але    │   │ витрати терпимі  │
   │ витрати з'їдають │   │ n=77 досяжне     │
   └──────────────────┘   └──────────────────┘
```

**Усе, що ми тестували, лежить ліворуч від вікна:**

| Що | Едж | Де |
|---|---|---|
| фіксинги (*JF* 2024) | ~0.5 п/лег | ліворуч |
| сесійна сегментація (*JMCB* 2013) | ~0.2 п/сесію | ліворуч |
| sweep-патерни №88 | 0 | ліворуч |
| 24 напрямкові ознаки | 0 | ліворуч |

## Правило

**Перед тим як тестувати гіпотезу — оцінити очікуваний едж у пунктах і перевірити, чи він потрапляє у вікно.**

- Едж < 10 п на угоду → гіпотеза мертва **до прогону**, скільки б спостережень не було. Не витрачати час.
- Едж ≥ 10 п → перевіряти, `n ≈ 77` достатньо.

## Що це означає змістовно

Едж 10+ пунктів — це **13% денного ATR EURUSD**. Такого розміру не буває у мікроструктурних патернів: вони живуть у діапазоні 0.5–3 п за побудовою. Отже механічний едж у цьому вікні — це вже не «фігура на графіку», а **подія**: макро-реліз, зміна режиму, структурний потік.

> Дві стіни не залишають простору посередині. Три роки роботи над патернами M15 були витрачені на область, де едж **не може** бути достатнім — незалежно від того, наскільки добре його шукати.

## Як зсунути стіну витрат

Єдиний важіль — зменшити `c`. ECN-виконання (raw spread 0.1–0.3 + комісія) дає `c ≈ 1.0` замість 2.0, і поріг вікна падає до 5 п.

Перерахунок наших кандидатів при `c = 1.0` **нічого не рятує**: фіксинги 6 п витрат проти 2.9 п валового, сегментація 504 п проти 96 п. Удвічі дешевше виконання зсуває стіну, але не настільки, щоб вони пройшли.

> Зв'язок: [[#A10]] пояснює, **чому** витрати домінують (`E_нуля ≈ −c/(SL+c)`); [[#A14]] — чому малий едж не виміряти; A16 з'єднує обидві стіни в одне правило відбору гіпотез **до** прогону.

# 📐 A17. Запас міцності порогового правила (виміряно 2026-08-25)

## Що виявилось

Звірка двох незалежних фідів — TradingView проти Dukascopy, 9 588 спільних барів M15, 100 торгових днів:

| Поле | медіана | p90 | max |
|---|---|---|---|
| open | 0.10 п | 0.30 п | 7.3 п |
| **high** | **0.10 п** | **0.20 п** | 6.9 п |
| **low** | **0.10 п** | **0.20 п** | 6.3 п |
| close | 0.10 п | 0.20 п | 6.1 п |

Дані практично тотожні. **Але 16% торгових днів дали різний набір sweep-подій.**

Причина: детектор — строга нерівність **без допуску**.

```
bar.high > asia_high  AND  bar.close < asia_high
```

Розбіжність 0.1 пункта перевертає подію повністю: була — не стало.

## Запас міцності

```
margin = min(глибина проколу, відстань зворотного закриття)
```

На 231 події №88: **медіана 1.0 п**, p10 = 0.2 п. Тобто **10.8% подій мають запас ≤0.2 п** — рівно на рівні шуму фіду, **20.3% ≤0.3 п**.

## Правило

**Будь-яке правило з пороговою нерівністю по екстремуму бару зобов'язане супроводжуватись виміром запасу міцності.**

| Медіанний запас | Висновок |
|---|---|
| **< 0.5 п** | 🛑 стратегія міряє **фід**, а не ринок — результат не переноситься нікуди |
| 0.5 – 1.0 п | ⚠️ перевірити, яка частка прибутку приходить з подій біля порога |
| **> 1.0 п** | ✅ прийнятно |

## Чому №88 вціліла саме за цим критерієм

| Група за запасом | Частка угод | Частка прибутку |
|---|---|---|
| ≤ 0.3 п | 15% | **4.4%** |
| > 2 п | 30% | **75%** |

Прибуток формують **глибокі** свіпи, яких шум фіду не стирає. Монте-Карло реального шуму фіду (60 ресемплів): **100% прогонів прибуткові**, winrate ніколи не нижче 67.6%.

Якби залежність була зворотною — тобто прибуток жив би на подіях біля порога — стратегію треба було б викидати незалежно від будь-яких CI.

> Це **не** реабілітація №88. Її закрито за іншою підставою — нульовий надлишок над нулем на сліпих вікнах. A17 лише каже, що причина смерті **не** в фіді.

## Форвард-очікування

На живій торгівлі **1–2 угоди на місяць у брокера не збігатимуться з бектестом** — з'являться зайві або зникнуть очікувані. Це нормальний шум фіду, а **не** доказ поламаного детектора.

Без цієї поправки перша ж «пропущена» угода читатиметься як збій.

# 🔗 A19. Залежні тести не додають доказу (виміряно 2026-08-25)

## Випадок

Round-number гіпотеза дала **16 комірок з одним знаком**, до −0.44R, p < 0.0001, проходила BH і Bonferroni. Виглядало як найміцніша знахідка проєкту.

На сліпому вікні: **Δ = +0.104R**, знак **протилежний**, p = 0.774. Не відтворилось нічого.

## Чому ілюзія була переконливою

Ті 16 комірок будувались на:
- **тих самих подіях**
- поділених на **ті самі групи**
- виміряних на **вкладених горизонтах** (N=1 ⊂ N=2 ⊂ N=4 ⊂ N=8…)

Це **одне спостереження, показане шістнадцять разів.**

> **Bonferroni і BH поправляють на КІЛЬКІСТЬ тестів, а не на їхню ЗАЛЕЖНІСТЬ.**

Шістнадцять залежних тестів несуть інформацію приблизно одного незалежного. Поправка ділить α на 16 і створює враження суворості там, де ефективних ступенів свободи одиниці.

## Правило

Перед тим як рахувати «скільки комірок узгоджені», відповісти:

| Питання | Якщо «так» — комірки залежні |
|---|---|
| Комірки будуються на **одній вибірці подій**? | ✓ |
| Горизонти **вкладені** один в одного? | ✓ |
| Групи розбиття **одні й ті самі**? | ✓ |
| Якорі **корельовані** між собою? | ✓ |

**Кількість узгоджених залежних комірок — не доказ.** Доказ дають:
- **незалежна вибірка подій** (інший період, інший інструмент),
- або **ортогональні** розрізи, що не переюзовують одні й ті самі угоди.

## Похідне: малі групи гуляють самі

Група `<5п` містила **18% подій** при `sd(R) ≈ 0.9`. Її середнє коливається на **±0.4R** від чистої випадковості — тобто на весь розмір «ефекту», який ми міряли.

**Перед інтерпретацією різниці груп — рахувати `sd/√n` кожної групи.** Якщо він порівнянний з різницею, різниця нічого не означає.

# ⛔ A20. MDE рахується ПЕРЕД витрачанням сліпого вікна

## Помилка, зроблена 25.08.2026

Останнє недоторкане вікно `blind2024h1` витрачено на перевірку ефекту **0.425R**. MDE того вікна виявився **0.617R**.

Вікно **фізично не могло** виявити те, що мало перевірити. Прогін не підтвердив і не спростував — він не мав потужності зробити ні того, ні іншого.

Розрахунок потужності стояв у плані **після** прогону. Резерв спалено дарма.

## Правило

**Перед будь-яким використанням сліпого вікна — окремий крок:**

```
1. оцінити розмір ефекту, який перевіряється        (з попереднього прогону)
2. порахувати MDE вікна при очікуваному n і поділі груп
3. MDE > очікуваного ефекту  →  СТОП, вікно не витрачати
```

Це не рекомендація і не крок «за можливості». Сліпе вікно **одноразове**: витратив — воно перестало бути сліпим назавжди, незалежно від того, чи дав прогін відповідь.

## Особливо — про поділ на групи

Очікували 112 подій. Фактичний поділ вийшов **20 / 39 / 53** — різко несиметричний.

MDE **різниці двох середніх** визначається **меншою** групою. Двадцять подій при `sd ≈ 0.93` не дають нічого.

**Рахувати MDE для найменшої групи, не для загального n.**

## Що з цього випливає організаційно

Справді сліпих вікон у проєкті **не залишилось** (`data/RESERVE_STATUS.md`). Наступна out-of-sample перевірка можлива **тільки на нових даних**.

Перенарізка наявних файлів out-of-sample **не створює** — вікно, на яке вже дивились в іншому контексті, сліпим не є.

> Зв'язок: [[#A14]] каже рахувати MDE перед висновком «ефекту немає». A20 каже рахувати його ще раніше — перед витратою невідновного ресурсу.
