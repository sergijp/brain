# ADR-2026-09-07 — Приватний CGVirtualDisplay замість залежності від BetterDisplay

**Status:** accepted
**Date:** 2026-09-07

## Контекст

Щоб macOS вважала, що є другий монітор, потрібен віртуальний дисплей. У macOS
**немає публічного API** для його створення. Варіанти:

1. приватні класи CoreGraphics (`CGVirtualDisplay` та ін.) — те, на чому
   побудований BetterDisplay;
2. вимагати від користувача поставити BetterDisplay і віддавати створений ним
   екран через `--display <id>`;
3. DriverKit — Apple не дає family для віртуального дисплея, відпадає.

Тула для особистого користування, App Store не цілимо — головне заперечення
проти приватного API (модерація) не діє.

## Рішення

Використати приватний API, але **не покладатись на нього жорстко**:

- ObjC-шим `SBVirtualDisplay` звертається до класів лише через
  `NSClassFromString` + неформальні декларації селекторів на `NSObject`. Жодного
  посилання на приватні класи під час лінкування — якщо Apple їх прибере,
  `+isSupported` поверне `NO`, а не впаде процес при старті;
- дескриптор годується і `setQueue:`, і `setDispatchQueue:` — Ventura має
  обидва, новіші системи лишили другий;
- `--display <id>` лишається повноцінним шляхом, тож BetterDisplay — робочий
  фолбек, а решта пайплайну від приватного API взагалі не залежить.

Сигнатуру знято **інтроспекцією рантайму на живій системі**, а не з пам'яті чи
з чужих заголовків.

## Альтернативи (відкинуті)

| Варіант | Чому відкинули |
|---------|----------------|
| Тільки BetterDisplay | Зайва зовнішня залежність там, де свій код — 100 рядків |
| Тільки приватний API, жорстко | Один апдейт macOS — і тула мертва без обхідного шляху |
| DriverKit | Apple не надає family для віртуального дисплея |

## Наслідки

**Позитивні:**
- тула самодостатня, нічого доставляти не треба;
- зламається м'яко, з фолбеком, а не падінням.

**Негативні / трейдофи:**
- приватний API може змінитись у будь-якому оновленні;
- перевірено лише на Ventura 13.7.8 Intel; на M1 ще не запускалось.
