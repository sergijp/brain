# Проект: screenbridge — власна тула для другого монітора

## Мета сесії

Зробити з iMac 27" 2017 другий екран для MacBook Pro M1. Target Display Mode на
цій моделі не працює (Apple прибрала його з Retina-iMac), тому кабельного шляху
немає. Duet Display вміє це, але платний — вирішили написати свою заміну.

## Виконано

| # | Задача | Результат |
|---|--------|-----------|
| 1 | Розібрати, чому TDM не працює | iMac 2017 = `iMac18,3`; Thunderbolt 3 порти лише на вихід. Кабельного варіанту не існує |
| 2 | Перевірити приватний `CGVirtualDisplay` | Інтроспекцією рантайму знято точну сигнатуру 4 класів. API живий на Ventura 13.7.8 |
| 3 | Довести, що віртуальний екран створюється | Створено 2560×1440 pt / 5120×2880 px (HiDPI), знищено чисто |
| 4 | Каркас проєкту | SPM, 4 таргети, без зовнішніх залежностей. Swift 5.9 + ObjC-шим |
| 5 | Пайплайн хоста | ScreenCaptureKit → VideoToolbox H.264 (low-latency) → Network.framework + Bonjour |
| 6 | Пайплайн клієнта | TCP → `CMSampleBuffer` → `AVSampleBufferDisplayLayer` (апаратне декодування) |
| 7 | Зворотний канал вводу | `NSEvent` монітор → JSON → `CGEventPost` з мапінгом у координати екрана |
| 8 | Діагностичні режими | `--test-pattern` (хост, без дозволів) і `--verify` (клієнт, без GUI) |
| 9 | Наскрізна перевірка | 720p60: 498 кадрів, 60.6 fps, 0 втрат, 0 помилок декодування — PASS |
| 10 | Універсальна збірка | `build.sh --universal` → arm64 + x86_64 в одному бандлі + `.app` з ad-hoc підписом |

## Проблеми й як вирішили

- **Bug: тест віртуального дисплея зламав розкладку екранів iMac.**
  - **Причина:** поява третього дисплея змушує macOS переузгодити конфігурацію.
    Основний екран злетів зі скейлу 3200×1800 на 2560×1440, ультраширокий
    переїхав з (3200, 211) на (5120, 0). Після знищення віртуального екрана
    **не відкотилось**.
  - **Фікс:** `DisplayArrangement.capture()` / `.restore()` — знімок режиму й
    позиції кожного екрана до створення віртуального, застосування назад при
    виході. Вбудовано в `ManagedVirtualDisplay`, викликається і на Ctrl-C.

- **Bug: клієнт перепідключався 13 разів за 8 секунд, доходив 1 кадр.**
  - **Причина (знайдена інструментуванням, не здогадкою):** одне `NWConnection`
    до Bonjour-ендпоінта відкриває **кілька TCP-з'єднань одночасно** — Happy
    Eyeballs гонить IPv6 проти IPv4. Лог хоста: `accept from ::1.51664` і
    `accept from 192.168.5.4:51665` у ту саму мілісекунду. Хост трактував друге
    як «новий клієнт» і вбивав перше.
  - **Фікс:** вхідне з'єднання тепер лише *кандидат*; воно стає активним
    клієнтом, коли надішле валідне повідомлення. Програш Happy Eyeballs нічого
    не шле і відпадає сам. Побічно вирішило й те, що `nc -z` проба більше не
    рахується клієнтом.

- **Bug: `scheduleReconnect` занулював поточне з'єднання при помилці старого.**
  - **Причина:** викликався і зі `stateUpdateHandler`, і з `receive`, без
    перевірки, чи це те саме з'єднання. Кожна помилка плодила дубль.
  - **Фікс:** `scheduleReconnect(from:)` звіряє ідентичність через `===`.

- **Хибний слід:** спершу 7 кадрів за 8 с у debug-збірці виглядало як проблема
  пайплайну. Насправді — попіксельний генератор тестового патерну без
  оптимізації. У release одразу 30/30 fps. Урок: заміри продуктивності Swift у
  debug не мають сенсу.

## Артефакти

- **Код:** `~/Data/Source/screenbridge/`
  - `Sources/CGVirtualDisplayShim/` — ObjC-шим приватного API (лише селектори,
    жодних посилань на приватні класи при лінкуванні)
  - `Sources/ScreenBridgeCore/` — протокол, фреймінг, збереження розкладки
  - `Sources/ScreenBridgeHost/` — захоплення, кодек, сервер, ін'єкція вводу
  - `Sources/ScreenBridgeClient/` — мережа, рендер, перехоплення вводу, верифікатор
- **Документація:** `README.md` (220 рядків, укр.), включно з чесним списком
  неперевіреного
- **Команди:**
  ```bash
  ./build.sh --universal
  ./build/ScreenBridgeHost.app/Contents/MacOS/ScreenBridgeHost --virtual 2560x1440
  ./build/ScreenBridgeClient.app/Contents/MacOS/ScreenBridgeClient
  ```

## Що лишилось неперевіреним

Розробка велася на iMac, а хост має жити на MacBook — тому без дозволів
лишились неперевіреними саме ті шматки, що їх вимагають:

- **ScreenCaptureKit** (потребує Screen Recording) — реального захоплення екрана
  не запускали жодного разу;
- **ін'єкція вводу** (потребує Accessibility);
- **arm64** — бінарник універсальний, але на M1 не запускався;
- реальна затримка й поведінка по Wi-Fi.

Перший запуск на MacBook треба починати саме з цих трьох пунктів.

## Друга частина сесії — GUI, DMG, повернення до свого екрана

### Мета

Три вимоги від користувача: DMG-інсталятори на обидві машини; іконка в menu bar
зі станом і перемикачем шарінгу; можливість на iMac повернутися до власного
екрана.

Третя вимога виявилась критичною, а не косметичною: вікно клієнта має рівень
вище за menu bar, тож без окремого механізму до menu bar просто не дотягнутися.

### Виконано

| # | Задача | Результат |
|---|--------|-----------|
| 11 | Пайплайн хоста винесено в `HostController` | запуск/зупинка на льоту, а не лише при старті процесу |
| 12 | Menu bar хоста | стан, живі fps/Mbps, Start/Stop, вибір джерела, fps, бітрейт, дозволи |
| 13 | Menu bar клієнта | стан, список хостів через Bonjour, вибір локального екрана |
| 14 | Показати/сховати віддалений екран | ⌃⌘D глобально + пункт меню |
| 15 | Глобальний хоткей | Carbon `RegisterEventHotKey` — **не потребує Accessibility**, на відміну від `NSEvent` global monitor |
| 16 | Налаштування в `UserDefaults` | GUI-застосунок із Finder не має аргументів командного рядка |
| 17 | `LSUIElement` | обидва — menu bar агенти, без іконок у Dock. Підтверджено `lsappinfo`: `type="UIElement"` |
| 18 | DMG | один універсальний образ 868 KB на обидві машини + Applications-симлінк + інструкція |
| 19 | CLI збережено | з аргументами обидва працюють як раніше, включно з `--test-pattern` і `--verify` |

### Ключові рішення

- **CLI не викинуто, а лишено як другий режим.** Без аргументів — menu bar,
  з аргументами — термінал. Діагностичні режими без дозволів лишились доступними,
  і саме ними перевіряється збірка.
- **Схований клієнт не декодує взагалі.** Кадри відкидаються до появи keyframe,
  при поверненні надсилається `requestKeyframe`. Інакше декодер малював би сміття
  з дельта-кадрів без опорного.
- **Carbon замість NSEvent для глобального хоткея** — єдиний спосіб мати
  системну гарячу клавішу без дозволу Accessibility.

### Проблеми й як вирішили

- **Bug: `BridgeServer` ніколи не дивився на стан `NWListener`.**
  - **Причина:** у Network.framework невдала прив'язка до порту приходить
    асинхронно через `stateUpdateHandler`, а не кидається з `start()`. Хост міг
    рапортувати «Waiting for a client…», фактично не слухаючи нічого.
  - **Фікс:** `onListenerReady` / `onListenerFailed`; статус «чекаю клієнта»
    ставиться лише коли listener справді `.ready`.
  - **Чесно:** знайдено під час розслідування одноразового «Connection refused»,
    першопричину якого до кінця **не** доведено. Виправлено клас збою, щоб
    наступного разу він був видимий, а не тихий.

- **Bug: лог клієнта був порожній при перенаправленні у файл.**
  - **Причина:** stdout блоково буферизується, SIGTERM викидає незлитий буфер.
  - **Фікс:** `setvbuf(stdout, nil, _IOLBF, 0)` в обох застосунках.

- **Хибний слід:** побачивши `lsof` з `IPv6 *:port (LISTEN)`, вирішив, що сокет
  IPv6-only. Перевірка `nc` на чотири адреси спростувала: всі приймаються,
  `net.inet6.ip6.v6only: 0`. Сокет дуальний, гіпотеза була хибна.

### Як перевіряв без дозволів і без можливості натиснути хоткей

- **Рендер:** додано `--stats` — друкує стан `AVSampleBufferDisplayLayer` і
  скільки кадрів реально намальовано. Результат: `layer rendering`, 60–62 fps,
  три прогони поспіль.
- **Показати/сховати:** тимчасовий прапорець `--toggle-test`, який перемикав
  видимість за таймером; стан вікна звірявся через `CGWindowListCopyWindowInfo`
  (метадані вікон дозволу не потребують). Схований стан: 0 fps і вікна немає в
  списку. Після перевірки прапорець прибрано, регресію прогнано заново.
- **Menu bar:** у списку вікон видно два вікна 35×24 на шарі 25 — це і є
  іконка статусу (macOS створює по одному на кожен екран).

### Артефакти

- `build/ScreenBridge.dmg` — 868 KB, `x86_64 arm64`
- Нові файли: `HostController.swift`, `HostMenuBar.swift`, `GlobalHotKey.swift`
- `build.sh` тепер робить `.app` + DMG; `--no-dmg` зупиняється на бандлах

### Лишається неперевіреним (без змін)

ScreenCaptureKit, ін'єкція вводу, виконання на arm64, фактичне натискання ⌃⌘D,
реальна затримка. Усе це потребує дозволів або машини, яких у сесії розробки
не було.

## Четверта частина — підключення з боку MacBook

### Мета

Користувач: «щоб я з макбука міг підключитись і щоб аймак був як монітор».
Напрямок **картинки** був правильний із самого початку, а от напрямок **ініціації**
— зворотний: підключався iMac, шукаючи MacBook. З MacBook не було видно жодного
екрана й не було до чого підключатись.

### Виконано

| # | Задача | Результат |
|---|--------|-----------|
| 25 | Двонаправлений Bonjour | хост оголошує `_screenbridge._tcp`, екран — `_sbscreen._tcp` (ім'я сервісу ≤15 символів) |
| 26 | Вихідні з'єднання на хості | `BridgeServer.connect(to:)` — набраний назовні сокет іде в той самий пул кандидатів |
| 27 | Вхідні на клієнті | `advertiseAsScreen(name:port:)` + `NWListener` |
| 28 | Меню **Connect To** | список екранів у мережі + `Connect Automatically` (типово увімкнено) |
| 29 | **Open at Login** на клієнті | `SMAppService.mainApp` — iMac стає постійно доступним монітором |
| 30 | `--listen-only` | режим для перевірки нового напрямку без GUI |

Хто відкрив сокет — протоколу байдуже: хост усе одно та сторона, що шле відео.
Тому напрямок ініціації додався без змін формату на дроті.

### Проблема

- **Bug: хост знаходив екран і підключався, але кадри не йшли.**
  - **Причина:** дзеркальне відображення бага, який я вже виправляв на хості.
    З'єднання до Bonjour-ендпоінта відкриває кілька TCP (Happy Eyeballs), а клієнт
    при кожному вхідному безумовно скасовував попереднє — і вбивав саме те, на якому
    хост зупинився.
  - **Фікс:** `BridgeClient` переписано на ту саму модель кандидатів, що й
    `BridgeServer`: вхідне з'єднання — кандидат, активним стає те, яке принесло
    валідне повідомлення; hello шлеться на кожного кандидата, свій `WireParser`
    на з'єднання.
  - **Урок:** коли протокол став симетричним, симетричним став і баг. Варто було
    одразу винести модель кандидатів у спільний код замість дублювати логіку.

### Перевірено

Три напрямки, усі PASS, нуль помилок декодування:
MacBook → екран (488 кадрів), екран → адреса (490), обидва через Bonjour (533).
Плюс наскрізна перевірка через GUI: хост із `Start Sharing at Launch` сам знайшов
оголошений екран і пішов у 62 fps.

### Артефакти

Інструкцію оновлено під новий порядок: iMac налаштовується один раз (+ Open at
Login), уся дія — з MacBook. Додано знімок підменю **Connect To**.

## П'ята частина — іконки в рядку меню

### Проблема

Обидва застосунки використовували **ті самі два символи** (`display` і
`rectangle.on.rectangle`), різнячись лише станом. Я сам на цьому спіткнувся під час
знімання: клікнув по «хосту» — відкрилось меню клієнта.

### Що відкинуто (перевірено рендером, не міркуванням)

- **Колірний тінт як індикатор стану.** На темному рядку меню акцентний колір
  виглядає майже чорним — іконка читається як «вимкнено», а не «активно».
  Додатково: `contentTintColor` взагалі не діє, якщо `isTemplate = false`.
- **Товщина як індикатор стану.** Жирний `desktopcomputer` на 16 pt втрачає
  підставку й перетворюється на пляму.
- **`macbook`** — такого символу на Ventura немає, є `laptopcomputer`.

### Рішення

`MenuBarIcon` у `ScreenBridgeCore`: **силует машини несе ідентичність і ніколи не
змінюється** (ноутбук — хост, моноблок — екран), **стан несе окрема мала крапка**,
домальована в композит. У template-зображенні важлива лише альфа, тож крапка
переймає тінт рядка меню автоматично.

### Як обирали

Відрендерив 4 варіанти × 2 стани **у справжньому рядку меню** і зняв екран —
судити іконку 16 pt за назвою SF Symbol безглуздо. Користувач обрав «форму машини»,
а слабке місце цього варіанта (жирний моноблок) я замінив на крапку.

### Артефакти

- `Sources/ScreenBridgeCore/MenuBarIcon.swift`
- `docs/icon-choices.png` — порівняльний рендер 4 варіантів
- Знімки 01/02/04 в інструкції перезняті; знімок 08 лишився чинним, бо обрізаний
  нижче рядка меню

## Шоста частина — чи можна зробити це нативною функцією macOS

### Питання

Користувач: «щоб воно працювало як стандартна функція macOS, тобто я шарю екран
Apple TV або iPad».

### Відповідь: ні, і це заблоковано Apple на рівні заліза

**Перевірено на самій машині, а не з документації:**

- `hw.model` = `iMac18,3` (2017);
- у System Settings → Загальні → **AirDrop і Handoff** є лише Handoff та AirDrop,
  пункт **«Приймач AirPlay» відсутній взагалі** — вмикати нічого;
- при цьому в мережі `_airplay._tcp` оголошується сторонній MacBook Pro, тобто
  механізм працює, але лише на підтримуваному залізі.

Apple обмежує «AirPlay to Mac» моделями iMac 2019+ і iMac Pro 2017. Sidecar —
лише iPad, закритий протокол, не емулюється.

**Теоретичний обхід** — реалізувати власний AirPlay-приймач (як AirServer,
Reflector, UxPlay). Тоді iMac з'явився б у нативному меню Screen Mirroring, але:
режим «Use As Separate Display» Apple лишає своїм пристроям, стороннім дістається
**лише дзеркалення** — тобто гірший результат, ніж уже є. Плюс реверс-інжиніринг
шифрованого протоколу, який ламається з оновленнями. **Не перевірено на практиці**,
знання по комерційних аналогах.

### Що зроблено натомість

Наблизити свою тулу до «просто працює»:

| # | Задача | Результат |
|---|--------|-----------|

## Девʼята частина — перший запуск у користувача, і справжній баг

### Два хибні сліди й один справжній

1. **Gatekeeper на Sequoia** — діалог «потрібно оновити» звучить як несумісність
   бінарника, але діагностика показала: підпис `valid on disk`, бінарник
   `x86_64 arm64`, `Info.plist` OK, виконуваний біт на місці. Причина —
   `com.apple.quarantine` плюс відсутність нотаризації. Формулювання Apple
   вводить в оману.

2. **Справжній баг: захардкоджені порти в ефемерному діапазоні.**
   Після зняття карантину застосунок запустився, але `lsof` показав, що процес
   **не має жодного сокета**. Порт 51223 у той момент займав **TradingView** під
   вихідне зʼєднання.
   - **Причина:** macOS роздає локальні порти вихідних зʼєднань з 49152–65535.
     Я вибрав 51222/51223 — усередині цього діапазону. Тобто чужий трафік міг
     будь-коли забрати порт, і listener не піднімався.
   - **Фікс:** екран слухає на порту від системи (`NWListener(using:)` без порту)
     — його адресу все одно розносить Bonjour. Хост має дефолт **45222** (поза
     ефемерним діапазоном) і при збою переходить на системний порт, повідомляючи
     реальний номер.
   - **Перевірено відтворенням умови:** зайняв 45222 через `nc -l`, прогнав —
     PASS, 479 кадрів, у лозі «Listening on port 54730 (requested 45222 was taken)».

### Що врятувало розслідування

Раніше додана видимість збоїв `NWListener` — застосунок сам показав у меню
«Не вдалося оголосити цей екран…». Без цього довелося б шукати навпомацки.
Це другий раз, коли ця зміна окупилася.

### Урок

Фіксований порт у діапазоні 49152–65535 — латентний баг, який спрацьовує
випадково й рідко. Для сервісів, що знаходяться через Bonjour, фіксований порт
не потрібен узагалі.

## Десята частина — аудит прогалин, і три справжні баги

Користувач попросив перевірити всі прогалини. Виявилось, що дозволи Screen
Recording і Accessibility **успадковуються** бінарниками, запущеними з оболонки
claude (у неї вони видані). Це відкрило доступ до того, що я місяцями позначав
як «не перевірено».

### Закрито найбільші прогалини

| Що | Результат |
|---|---|
| ScreenCaptureKit, реальний екран | 57 кадрів 2560×1080, 0 помилок |
| Ін'єкція вводу | курсор став рівно в (4480, 751) — мапінг точний |
| Віртуальний екран + захоплення (робочий сценарій) | PASS, 1440×900 |
| Режим 2× | PASS |
| Відкат порту при колізії | PASS |

Тест вводу: власний мінімальний клієнт на Python, що вручну збирає кадр протоколу
(`[type=1][len BE][JSON]`) і шле `{"mouse":{"_0":{…}}}` — Swift Codable для enum з
асоційованим значенням кодує саме так.

### Баг 1: порти в ефемерному діапазоні

51222/51223 лежать у 49152–65535, звідки macOS роздає локальні порти вихідних
зʼєднань. TradingView забрав 51223 — listener не піднявся, процес лишився **без
жодного сокета**. Фікс: екран слухає на порту від системи (Bonjour розносить
адресу), хост має дефолт 45222 і відкат на системний.

### Баг 2: `1x1` — головний

Віртуальний екран потрапляє у список активних **миттєво, але як заглушка 1×1**;
справжній розмір приходить лише через ~1.5 с. Моє очікування перевіряло
`pointWidth >= 1` — і 1×1 цю умову проходило. Далі округлення до парного
перетворювало 1 на **0**, і VideoToolbox падав з `kVTParameterErr (-12902)`.

Знайдено зондом, який друкував стан екрана кожні 250 мс:
```
t=0.00s size=1x1
t=1.50s size=1440x900
```

Фікс: чекати на **саме запитану** геометрію, а не на «щось ненульове».

### Баг 3: самоблок головної черги

Черга дескриптора віртуального екрана — **головна**. Очікування через
`Thread.sleep` на головному потоці блокувало саме ту чергу, через яку CoreGraphics
добудовує екран. Фікс: крутити run loop, поки чекаємо.

### Дві відкинуті гіпотези

- «`setQueue:` проти `setDispatchQueue:`» — перевірив усі три варіанти
  (старий / новий / обидва), результат ідентичний. Селектор ні до чого.
- «залежить від роздільності» — усі чотири розміри падали однаково.

### Урок

Шлях «створити віртуальний екран і зняти з нього» **жодного разу не проходився
цілком** — я перевіряв створення екрана окремим ObjC-тестом (який крутив run loop
і тому працював) і захоплення окремо на тестовому патерні. Три баги жили саме на
стику, якого не торкався жоден тест.

## Одинадцята частина — якість після першого реального запуску

Користувач нарешті запустив на MacBook. Три зауваження, усі з конкретними причинами.

### Роздільність не збігалася з панеллю

Віртуальний екран створювався з пресету, обраного наосліп. Додано `Control.screenInfo`:
клієнт при підключенні повідомляє розмір свого екрана, хост перебудовує віртуальний
під нього (`matchVirtualDisplay`, з захистом від циклу). Пункт меню
«Підлаштувати під екран клієнта», типово увімкнений.

### Мутність — баг плюс компроміс

- **Баг:** шар рендера на клієнті лишався в `contentsScale = 1`, тож картинка
  масштабувалася вдруге вже композитором — втрата різкості двічі. Фікс:
  `layer.contentsScale = window.backingScaleFactor` у `viewDidMoveToWindow`.
- **Компроміс:** потік ішов у точковій роздільності, а панель iMac учетверо
  щільніша. Перемикач «2×» замінено на регулятор **Чіткість** (1× / 1.5× / 2×)
  з обмеженням зверху реальним backing store.

Перевірено декодування на iMac 2017: 3840×2160 і 5120×2880 — обидва PASS, нуль
помилок. Тобто Radeon Pro 575 тягне 5K H.264.

### Курсор підвисав

Малювався на хості й приїжджав у складі відео, тобто із затримкою всього ланцюжка.
Тепер `showsCursor = false` на хості, а клієнт **не ховає свій** курсор — рух
миттєвий, по мережі йдуть лише координати. Перемикач «Малювати курсор у відео»
повертає стару поведінку.

### Ввід не працював — і мовчки

`CGEventPost` без дозволу Accessibility **не падає, а нічого не робить**. Симптом:
курсор рухається (він локальний), але кліки не діють. Додано явне попередження в
меню: «Клавіатура й миша НЕ працюють / Немає дозволу Accessibility» — замість
самого лише пункту «Надати доступ…» десь нижче.

**Урок:** дозвіл, відсутність якого не викликає помилки, треба перевіряти й
показувати самому — інакше користувач бачить непрацюючу програму без пояснень.

## Дванадцята частина — аудит субагентами, і чому падав fps

Користувач попросив запустити субагентів. Двоє паралельно: аудит коду шляху
роздільності та дослідження меж ScreenCaptureKit і VideoToolbox. Обидва дали
знахідки, яких я сам не побачив.

### Головне: мовчазний перехід на програмний кодер

Вище певного розміру `VTCompressionSessionCreate` **успішний**, але low-latency
режим не надається — VideoToolbox тихо бере програмний кодер. Заміряно на Intel
iMac 2017: 3200×1800 → апаратний, 29.5 fps; 4800×2700 → програмний, 6.5 fps;
6400×3600 → 4.5 fps. Нуль втрачених кадрів, бітрейт 3-4 Мбіт/с при дозволених 50
— тобто впиралося не в мережу, а в швидкість кодування.

**Фікс:** режим «Авто» — цілитись у щільність панелі клієнта і знижувати масштаб,
доки кодер лишається апаратним. Індикатором служить доступність low-latency.

**Відкинуто:** `RequireHardwareAcceleratedVideoEncoder` як детектор — на цьому Mac
він відхиляє **всі** розміри, включно з робочими.

### Порожній екран не давав кадрів — і причина була в моєму фільтрі

ScreenCaptureKit гарантує перший кадр статусом `SCFrameStatusStarted`, а я
фільтрував **лише** `.complete` і цей кадр викидав. Статичний екран (віртуальний
до того, як на нього перетягнули вікно) не давав нічого. Додано приймання
`.started` + перевірку `CMSampleBufferGetNumSamples > 0`, плюс heartbeat раз на
секунду і синтетичний чорний кадр, якщо буфера ще нема.

### Знахідки аудиту коду, які виправлено

- **`matchedScreenSize` не скидався у `stop()`** — після зупинки й повторного
  запуску хост назавжди переставав підлаштовуватись під екран клієнта.
- **Хост викидав `backingScaleFactor` клієнта** (`case .screenInfo(_, _, _)`) —
  саме те, що потрібне, щоб автоматично обрати чіткість.
- **`contentsScale` ставився у `viewDidMoveToWindow`** — не спрацьовує при зміні
  масштабу екрана. Додано `viewDidChangeBackingProperties`.
- **Off-by-one на краю екрана:** нормалізована 1.0 мапилась на `origin + width`,
  тобто в перший стовпець сусіднього дисплея.
- **`CGDisplayPixelsWide` як запасний варіант** повертає точки, не пікселі.

### Артефакт тестування, який спершу здався багом

Хост і клієнт на одній машині: створення віртуального екрана перебудовує розкладку,
і клієнт устигає повідомити **вже змінений** розмір. У реальній схемі цього немає —
віртуальний екран на MacBook, а міряється екран iMac.

### Урок

Аудит субагентами дав те, чого не давало тестування: тести показували *що* повільно,
а читання коду і документації пояснило *чому*. Мовчазний фолбек на програмний кодер
неможливо було побачити з логів — він виглядав як успіх.

## Тринадцята частина — чорний екран на ручній чіткості

Користувач обрав «Різкіша»/«Максимальна» — чорний екран.

**Причина:** програмний кодер не просто повільний. Він не встигає за
ScreenCaptureKit у межах `minimumFrameInterval × (queueDepth − 1)`, SCK вичерпує
пул IOSurface і **перестає віддавати кадри взагалі**. На Intel це виглядало як
6 fps, на M1 — як повна зупинка.

**Фікс:** програмне кодування не приймається **ніколи**, навіть на ручний вибір.
Ручний масштаб став побажанням: хост знижує його, доки кодер лишається апаратним,
і показує в меню «Межа кодера: використано 1×, а не 2×» — щоб мовчазне зниження
не виглядало як несправність.

**Перевірено:** Авто / 1× / 1.5× / 2× — усі чотири дають 200+ кадрів і low-latency,
жодного чорного екрана. На Intel усі зводяться до 3200×1800; на M1 межа вища.

**Помилка в тестуванні, варта запам'ятовування:** zsh не розбиває незакавичену
змінну на слова, тож `$ARG` з `--scale 1` пішов одним аргументом, і три тести
«провалились» через мій скрипт, а не через код.

## Чотирнадцята частина — видимий стан звʼязку

Користувач: при відключенні зображення зависає замість повідомлення, а підключення
не показується взагалі.

**Зроблено:** типізований `BridgeClient.LinkState` (`waiting / searching /
connecting / connected / lost`) замість рядків, і `StatusOverlay` поверх відео.
`VideoView.reset()` викликає `flushAndRemoveImage()` і скидає format description,
тож стара картинка зникає, а не лишається під написом.

**Ключова деталь:** індикатор ховається не за подією «підключено», а коли
**реально прийшов кадр** — інакше «Підключено» відкривало б порожнє вікно.

**Перевірено вимірюванням:** під час трансляції середня яскравість кадру 93
(реальне відео), після розриву 29 (темний індикатор). Знімок стану розриву
підтверджує текст «Відключено / Хост припинив трансляцію».

**Обмеження:** у стані очікування вікна ще не існує (клієнт створює його при
показі), тож «Не підключено» видно лише якщо відкрити віддалений екран вручну.

## П'ятнадцята частина — зупинка потоку і гонка при перезапуску

Користувач: на «Різкіша» клієнт пише «Підключено, чекаю на зображення» і так
лишається; а після відключення й повторної спроби — «Start stream failed».

### Діагностика по живому

Підключився власним verify-клієнтом до його MacBook у мережі: **не прийшов навіть
конфіг відео** (SPS/PPS), не кажучи про кадри. Отже кодер не видавав нічого —
підтвердження, що вище певного розміру пайплайн стає зовсім, а не сповільнюється.

### Три виправлення

1. **Сторож (watchdog).** Якщо клієнт підключений, а кадрів немає понад 6 секунд —
   знизити масштаб на крок і перезібрати пайплайн. Сидіти в непрацюючому стані —
   ніколи не відповідь. Стеля масштабу лишається до кінця сесії: розмір, що вже
   нічого не дав, не дасть і вдруге.

2. **`Start stream failed` — гонка.** `stop()` не чекав на фактичну зупинку
   `SCStream` (він був `Task { await … }` без очікування), і новий старт міг
   початись раніше. Додано `stop(then:)`, який кличе продовження **після**
   зупинки; усі перезапуски (меню, підлаштування розміру, сторож) ідуть через нього.

3. **Повторна спроба в SCK.** Одразу після появи/зникнення дисплея
   `startCapture()` може відмовити; додано одну повторну спробу через 0.7 с.

### Чого перевірити не вдалось

Точний сценарій користувача (вимкнути/увімкнути з меню) на цьому iMac не
відтворюється: **GUI-застосунок тут не має дозволу на запис екрана** — він є лише
у процесів, запущених з оболонки. Тому перевірено суміжний шлях перезапуску (зміна
розміру під клієнта), який іде тим самим кодом: перезапуск проходить, помилки немає,
картинка відновлюється.

## Шістнадцята частина — HEVC, і два баги, що тримали чіткість на 1×

### Межа H.264 виявилась структурною

Дослідження (субагент) знайшло причину в заголовках SDK: константи профілів H.264 у
VideoToolbox зупиняються на **рівні 5.2** — MaxFS 9 437 184 семпли, тобто ~4096×2304.
Мій незалежний бенчмарк дав ту саму границю з точністю до пікселя: 4096×2304 = 69 fps,
4160×2340 = 3.8 fps. Вище — програмний кодер.

**HEVC** (`Main_AutoLevel`, рівень 6.x) дозволяє до 8192×4320. Додано підтримку:
`VideoConfig` тепер несе кодек і довільну кількість parameter sets (HEVC має три —
VPS/SPS/PPS), клієнт будує format description через
`CMVideoFormatDescriptionCreateFromHEVCParameterSets`.

**Перевірено:** iMac 2017 декодує HEVC 5120×2880 без помилок. Дослідження пояснює
чому: декодує Intel Quick Sync (HD 630), а не Radeon Polaris, обмежений 4K.

### Баг 1: сторож рахував мовчання до підключення клієнта

`lastFrameAt` виставлявся при старті шарінгу, а кадри йдуть лише коли є клієнт.
Якщо клієнт підключався пізніше ніж через 6 с, сторож бачив «мовчання» і **одразу
знижував чіткість, не давши надіслати жодного кадру**. Саме це тримало користувача
на 3200×1800 незалежно від налаштувань.

### Баг 2: стеля масштабу жила до кінця процесу

Знижена сторожем стеля не скидалась ніколи — одна невдала спроба назавжди
пришпилювала до 1×, і жоден вибір у меню це не міняв. Тепер `resetLimits()`
викликається при явному старті шарінгу й зміні налаштувань, але переживає
внутрішній перезапуск сторожа (інакше він одразу повертався б у розмір, що впав).

### Хибна тривога, що коштувала трьох раундів

Побачив «12 помилок декодування» і послідовно відкотив діапазон кольору, виправив
час життя вказівників, переробив кешування keyframe. Коли нарешті надрукував **код**
помилки — він був `noErr`: декодер повертав успіх без картинки, що для асинхронного
режиму нормально, а мій верифікатор рахував це збоєм. Регресія була **у
вимірювальному інструменті**. Виправлення вказівників лишив (реальна вада —
`UnsafePointer` на локальний масив), решту відкотив.

**Урок:** перш ніж відкочувати зміни через «регресію», надрукувати код помилки.

## Сімнадцята частина — чіткість вирішено, курсор доведено

Користувач: «Чіткість максимальна, кодек HEVC, все супер чітко». Тобто HEVC зняв
межу 4K і питання різкості закрите.

Лишився курсор: підгальмовує й інколи стрибає.

**Причина:** події миші йдуть **тим самим TCP-зʼєднанням**, що й відео. На
5120×2880 кадри великі, рухи стоять у черзі за ними й приходять пачкою — це
відчувається як затримка з наступним стрибком.

**Фікс — склеювання з обох боків:**
- клієнт шле не кожен мікрорух, а максимум один на 1/120 с, завжди найсвіжішу
  позицію; кліки, драги й прокрутка ніколи не склеюються і флашать чергу перед
  собою, щоб не зламати порядок;
- хост, отримавши в одній порції кілька рухів, застосовує лише останній —
  відтворювати застарілі означає малювати стрибки.

**Перевірено:** точний тест координат — курсор став у (4479.5, 750.5) при
очікуваних (4480, 751); піврозбіжність — наслідок власного ж фіксу краю екрана
(`width - 1`). Відео: PASS, нуль збоїв.

**Не зроблено:** окреме зʼєднання для вводу. Це радикальніше рішення проблеми
head-of-line blocking, але помітно складніше через логіку промоції зʼєднань.

## Вісімнадцята частина — курсор: гіпотезу спростовано вимірюванням

Користувач: курсор підгальмовує, і **менша чіткість — менше гальм**.

### Три невдалі виміри поспіль, усі через мій же інструмент

1. Перший вимірювач запускав **окремий процес** на кожну перевірку курсора в
   щільному циклі — сам крав CPU у кодера й міряв власне навантаження.
2. Переписаний на один процес — але підключався **другим клієнтом**, а хост віддає
   потік одному, тож вони по черзі виштовхували один одного.
3. Виправлено на «один клієнт приймає відео і міряє ввід» — але цільові координати
   лишились захардкоджені під ультраширокий екран, тож при захопленні головного
   курсор їхав правильно, а я чекав його не там.

### Чистий результат

| Роздільність | Медіана | 90% |
|---|---|---|
| 2560×1080 | 0.8 мс | 2.7 мс |
| 3200×1800 | 0.8 мс | 2.4 мс |

**Ввід доходить менш ніж за мілісекунду, і роздільність на це не впливає.**
Моя гіпотеза (ввід стоїть у черзі за відео) спростована.

Відстає не курсор — він локальний і миттєвий. Відстає **реакція вмісту**, бо вона
з'являється лише після повного циклу захоплення → кодування → передача →
декодування, а він прямо пропорційний розміру кадру. Це пояснює кореляцію з
чіткістю.

### Що зроблено

- Черга кадрів «у польоті» скорочена з 2 до 1. Перевірено на стабільному джерелі:
  375 / 372 / 377 кадрів для глибин 1 / 2 / 3 — тобто **пропускна здатність не
  страждає**, а найгірша затримка зменшується.
- Пріоритет черг вводу піднято до `userInteractive` (лишено, хоч вимір показав, що
  вузьким місцем воно не було).

### Урок

Три раунди пішли на боротьбу з власним вимірювальним інструментом. Перед тим як
робити висновок «система повільна», варто перевірити, чи не вимірюєш ти сам себе.
