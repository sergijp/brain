# Закриття технічного боргу після пересадок v2

## Мета сесії

Після завершення пересадок лишався список відкритих питань, більшість — знайдені
принагідно й відкладені на рішення власника. Власник сказав закрити все.

Перед роботою кожен пункт **перевірено в коді заново**, а не взято з нотаток —
один пункт (`phpunit.xml`) виявився вже неактуальним.

## Виконано

### 🔴 Фільтри CRUD протікали один в одного

`Filters::applyFiltersQuery` складав усі фільтри в одну спільну дужку. Досить було
одному вжити `orWhere` без власного групування — і через пріоритет AND над OR умова
розсипалась на решту.

Реальний випадок: фільтр квитків «Пасажира» (`name LIKE ? OR surname LIKE ?`) разом
із діапазоном дат давав **1598 рядків замість 1**.

Виправлено **в ядрі**, а не в окремому фільтрі: кожен фільтр тепер у власній дужці.
Плюс сам фільтр «Пасажира» групує свій OR — щоб намір був видно на місці.

Витоку даних не було: глобальні скоупи (`TicketScope`) лишаються зовні обгортки, тож
чужих квитків агент не бачив. Перевірено окремо — спершу я запідозрив саме витік і
помилився; ламалась точність вибірки, не доступ.

### 🔴 Партнерські API віддавали чужі ордери

`GlobalApi::orderinfo` і `getOrderWithTickets` у External / SiteApi / Busfor / PrivatBank
шукали ордер **тільки** за `uuid` або номером квитка. Вгаданий чужий ідентифікатор
віддавав повні дані замовлення з персональними даними пасажирів, а `reject`/`sell`
дозволяли скасувати чи продати чуже.

Додано фільтр за `member_id`. Перед цим перевірено на даних, щоб не зламати партнерів:

- кожен партнер має власний member (Busfor API — 43 937 ордерів, INFOBUS API — 12 778 тощо);
- `BookingService::book` записує туди автентифікованого користувача;
- `api_user` (підміна власника) у партнерських API не використовується — тільки в адмінці;
- `getOrderWithTickets` вживається лише в `reject`/`sell`, тобто над щойно створеним своїм ордером;
- ордери без власника — 1177, найновіший лютий 2026, за 90 днів жодного.

### Мертвий код і зламані роути

| Що | Стан | Дія |
|---|---|---|
| `POST /customer/registration` | роут живий, метод падав на неіснуючих `Website` і `Tenancy` | роут і метод прибрано |
| `BookingController::getPaymentForm` | 143 рядки, не в жодному роуті, всередині падав на `Tenancy::getTenant()` | видалено разом з осиротілими імпортами `Billing`, `LiqPay`, `JsonResponse` |
| `Mail\Admin\Tickets\TicketsSold` | клас спирався на неіснуючий `Website`; виклики закоментовані, один невживаний імпорт | файл видалено, імпорт прибрано |
| `ConvertData::convertToCurrenciesSite` | оголошений, не викликається ніде | видалено |

Публічну реєстрацію клієнтів свідомо **не відновлював**: вона де-факто не працювала,
а вмикати її мовчки — це публічний ендпоінт без підтвердження пошти й обмеження частоти.
Якщо знадобиться — окрема задача.

### activity_log — 853 МБ

1 239 615 рядків, з них 455 647 (36.8%) — автоматичні записи про `TripPrice` від нічної
генерації рейсів. Нові вже не з'являються (`Route::createTrip` перейшов на bulk insert,
якого обсервер Spatie не бачить).

Замість разового `DELETE` написано команду `php artisan activity-log:prune`:
`--dry-run`, `--days=N`, батчі з паузою, підтвердження на production. Разовим запитом
на пів мільйона рядків таблиця блокувалась би хвилинами, а в неї пишеться кожна дія оператора.

**На dev не запускав** — це не дає користі, а рішення чистити бойову базу лишається за власником.
Після видалення місце віддасть `OPTIMIZE TABLE`, і команда про це нагадує.

## Важливі рішення

| Рішення | Чому |
|---|---|
| Фікс фільтрів — у ядрі, не в одному фільтрі | наступний фільтр із `orWhere` відтворив би ту саму помилку |
| `member_id` додано в усі 5 місць одразу | лишити хоч одне означало б лишити діру |
| Реєстрацію клієнтів не відновлювати | вмикати публічний ендпоінт без rate limit і підтвердження пошти — гірше, ніж його відсутність |
| Чистку `activity_log` оформити командою | разовий DELETE блокує таблицю; команду можна прогнати з `--dry-run` на проді |
| На dev нічого не чистив | репетиція не дає користі, а дані видаляти без потреби не варто |

## Перевірка

- **76 тестів** (було 69). Нові: `PartnerOrderIsolationTest` (3), `FilterIsolationTest` (2).
- Фільтр після фікса: **1 рядок замість 1598**.
- В адмінці перевірено вручну: «Пасажира: Шваб» + дата 27 липня → порожньо (квитки Шваб на 3 серпня).
  До фікса вони показались би попри дату.
- `route:list` — 524 роути, завантажується без помилок.
- Жодного осиротілого посилання на видалений код (перевірено grep-ом).
