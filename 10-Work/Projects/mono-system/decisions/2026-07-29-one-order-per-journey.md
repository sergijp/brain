# ADR-2026-07-29 — Подорож з пересадками = ОДИН ордер

**Status:** accepted
**Date:** 2026-07-29
**Стейкхолдери:** власник продукту (рішення прийняте явно в діалозі)

## Контекст

Transfers v2 замінює ручне парування пересадок на автоматичний пошук стиковок через хаби.
Одна подорож складається з 2–3 плечей — окремих рейсів різних маршрутів.

Постало питання: як зберігати куплену подорож?

Початковий план (`TRANSFERS-V2-PLAN.md`, редакція до 2026-07-28) припускав **кілька ордерів**,
зв'язаних спільним `orders.journey_uuid`. Під цю модель у Фазі 1 навіть було створено колонку
`orders.journey_uuid` (міграція `2026_07_28_130200`).

Легасі-пересадки (`bookTransfer`) реалізовані саме так: плечі лежать у **різних** ордерах,
зв'язані через `tickets.parent_id`.

Обмеження, які визначили рішення:

1. **Сторонні API не можна чіпати.** `GlobalApi`, `ExternalApi`, `BusforApi` — для партнерів
   подорож має виглядати як **одна поїздка й один квиток**. Це прямий і категоричний вимог
   власника продукту. Кілька ордерів зламали б цю картину на рівні ресурсів.
2. **Платіжки прив'язані до ордера.** LiqPay/PrivatBank отримують один `orderId` і повертають
   один вебхук. Кілька ордерів на одну оплату означали б розподіл платежу між ордерами,
   часткові оплати, і нову категорію станів «оплачене плече 1, неоплачене плече 2».
3. **Пересадки не продаються окремо.** Власник продукту підтвердив: плече подорожі неможливо
   купити чи повернути окремо від решти. Отже, окремий ордер на плече не має бізнес-сенсу.

## Рішення

**Подорож — це один ордер із кількома квитками, по одному на плече.**

- `orders.trip_id` = рейс **першого** плеча
- квитки плечей зв'язані ланцюгом `tickets.parent_id`
- усі квитки подорожі мають **однаковий** `order_id`
- `orders.amount` = сума цін усіх плечей
- вхідна точка — `BookingService::bookJourney()`, одна транзакція на всю подорож

Розрізнення v2 і легасі: `Ticket::isJourneyLeg()` перевіряє, що в ланцюзі `parent_id`
є ≥2 квитки **в тому самому ордері**. Легасі-пересадки теж використовують `parent_id`,
але лежать у різних ордерах — тому проходять повз цю перевірку і працюють як раніше.

`orders.journey_uuid` залишилась невикористаною і **видалена** міграцією
`2026_07_29_120000_drop_journey_uuid_from_orders_table` (2026-07-29). Міграцію, що її
створювала, навмисно не прибрали: на dev вона вже відпрацювала, і видалення файлу
лишило б колонку в базі з осиротілим рядком у `migrations`.

## Альтернативи (відкинуті)

| Варіант | Чому відкинули |
|---------|----------------|
| Кілька ордерів + спільний `journey_uuid` | Ламає контракт сторонніх API (одна поїздка = один квиток); тягне multi-order checkout, розподіл платежу між ордерами, зміни у вебхуках платіжок, нові часткові стани оплати |
| Один ордер + один «синтетичний» квиток на всю подорож | Немає куди писати місце й ціну кожного плеча; посадка на плечі 2 не має що сканувати; неможливо частково скасувати рейс одного плеча |
| Розширити легасі `bookTransfer` під довільну кількість плечей | Легасі жорстко закладає рівно 2 плечі й ручне парування станцій; переписування було б більшим за нову реалізацію |

## Наслідки

**Позитивні:**

- Викреслено цілий пласт роботи, закладений у початковий план: multi-order checkout,
  зміни у вебхуках платіжок, синхронізація станів між ордерами, `journey_uuid` як сутність.
- Checkout працює без змін — окрім одного фіксу (див. нижче).
- Скасування й повернення природно каскадуються по ланцюгу `journeyChain()` у межах ордера.
- Сторонні API бачать один ордер із першим плечем як «поїздкою» — контракт не порушено.

**Негативні / трейдофи:**

- `orders.trip_id` для подорожі семантично неповний — це лише перше плече.
  Будь-який код, що рахує «від рейсу ордера», для подорожі побачить тільки плече 1.
  **Знайдений приклад:** `orderedTickets` у `GlobalApi`/`SiteApi` `OrderCreatedResource:123`.
- Неможливо повернути одне плече, лишивши решту. Це збігається з бізнес-правилом,
  але жорстко зафіксовано в архітектурі.
- Розрізнення v2/легасі тримається на неочевидному інваріанті «однаковий `order_id`».
  Без `isJourneyLeg()` легко зламати легасі, зачепивши v2.

**Що це блокує / unlocks:**

- Розблокувало Фази 3–4 без роботи над платіжками.
- Заблокувало можливий у майбутньому продаж окремих плечей — це буде зміна архітектури, не фіча.

**Побічна знахідка при реалізації:** у `BookingController` checkout рахував
`'amount' => $request->input('amount') * count($tickets)` — множив ціну одного квитка
на кількість. Для подорожі з різними цінами плечей це давало неправильну суму.
Це вже існуючий баг (проявлявся і на звичайних ордерах, де `client_discount` обнуляв ціну
одного квитка). Замінено на `$order->amount`.

## Перегляд

Переглянути, якщо:

- з'явиться вимога продавати або повертати окремі плечі подорожі;
- партнер зажадає бачити подорож як кілька окремих поїздок;
- виникне потреба в частковій оплаті подорожі.

У всіх трьох випадках це буде нове рішення, а не правка цього.
