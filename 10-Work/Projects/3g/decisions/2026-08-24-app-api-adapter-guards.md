## Контекст

`/api/v1/app` побудовано як шар тонких адаптерів над контролерами сайту
(`Api\TripController`, `Api\OrderController`, `Api\TicketsController`, `Api\Profile\*`).
Аудит виявив, що наявний код сайту в цьому контексті:

- шукає квиток/замовлення **без перевірки власника** (на сайті достатньо сесії) —
  для публічного API це IDOR;
- падає з 500 на кривому вводі (5 місць: неіснуюче місто, станція не з рейсу,
  невалідний хеш, кривий `passcount`, неіснуючий `trip_id`);
- читає параметри через `$request->get()`, який **не бачить JSON-тіла**;
- звужений глобальним `TicketScope` до замовлень технічного Member — застосунку
  видно 16.6% квитків;
- віддає помилки валідації зі **статусом 200** (`failedValidation()` без коду).

Той самий код обслуговує працюючий сайт.

## Рішення

**Усі виправлення — в адаптерах і middleware `/api/v1/app`. Контролери сайту
не змінюються.** Два свідомі винятки, де правка в адаптері неможлива:

1. `Api\ErrorReportsController::create` — контролер сам створює запис, тож `client_id`
   можна проставити лише там (для водія лишається `null`).
2. `Profile\PersonalDataRequest` — `email` без `unique` дозволяв зайняти чужу адресу;
   правило спільне для сайту й застосунку, і діра теж спільна.

Конкретні механізми:

| Проблема | Механізм |
|---|---|
| JSON не доходить до `get()` | middleware `NormalizeJsonInput`: JSON → request-бег + зміна Content-Type |
| `TicketScope` ховає 83% квитків | middleware `WithoutTicketScope`: no-op заглушка на час запиту, у `finally` — назад |
| IDOR | guard-и в адаптері **перед** делегуванням; трейт `Concerns\ResolvesOrder` |
| 500 на кривому вводі | перевірки існування/формату в `BookingController` перед делегуванням |
| Валідація зі статусом 200 | трейт `Concerns\ResolvesFormRequest`: міняє лише код на 422, тіло лишає |
| Покупка не потрапляє в кабінет | `app.client:optional` у публічній групі — заголовок `Client` для `/order/create` |

## Причина

Контролери сайту обслуговують продакшн-трафік і не покриті тестами. Будь-яка зміна
їхньої поведінки (статуси, видимість, формат) — це ризик для сайту заради застосунку.
Адаптер натомість ізольований: він діє лише на 27 маршрутах `/api/v1/app`, і його
регресію видно одразу.

Зворотний бік — дублювання перевірок: guard в адаптері шукає квиток, і делегований
метод шукає його ще раз. Прийнято свідомо як ціна за незмінність сайту. Виняток —
`TicketController::show()`, де подвійний пошук давав 500 (другий раз під `TicketScope`),
тож ресурс віддається напряму.

## Альтернативи

- **Правити контролери сайту.** Найменше коду, але змінює поведінку сайту в місцях,
  які ніхто не перевіряє автоматично.
- **Дати технічному Member право `tickets-visible-all`** замість `WithoutTicketScope`.
  Одна дія вручну, але знімає обмеження видимості і для сайту.
- **Свій набір контролерів для застосунку**, без делегування. Дублює бізнес-логіку
  бронювання — саме те, чого модуль уникає з самого початку.

## Ризики та мітигація

- `WithoutTicketScope` міняє статику моделі → відновлення у `finally`; перевірено, що
  скоуп повертається навіть після запиту, який завершився 500. Черга на `redis`, тож
  у джоби не протікає; при переході на `sync` або Octane — переперевірити.
- `NormalizeJsonInput` міняє `Content-Type` на form-urlencoded → код, що читає сире
  тіло за Content-Type, поводився б інакше; у цій групі такого немає.
- Зняття скоупу розширює видимість квитків при бронюванні → перевірено на 30 найближчих
  рейсах: розбіжність нульова, ризику подвійного бронювання немає.
- Ліміти частоти ключуються по IP+шлях, а не по `$request->user()` — інакше ліміт був би
  спільним на весь застосунок (користувач один). За зворотним проксі без `TrustProxies`
  ключ виродиться в IP проксі.

## Наслідки

- Два трейти в `Concerns/` — точка повторного використання для нових ендпоінтів застосунку.
- Гість працює з замовленням лише за `uuid`; числовий `orders.id` доступний тільки власнику.
- Помилки валідації застосунку — 422, сайту — як були, 200.
- `PersonalDataRequest` вимагає унікальності email **лише при зміні**: у базі 9 адрес
  на 18 клієнтів, безумовне правило заблокувало б їм збереження профілю.
