## Мета сесії

Продумати розбиття функціоналу 3g на **базову систему + модулі** з простим механізмом додавання/видалення; дослідити інтеграцію механізму ліцензування (окремий license-сервер з Ed25519 токенами).

Результат: **дизайн модуляризації варіант (b)** — власний легкий реєстр без зовнішніх фреймворків; система готова до подальшої реалізації поетапно.

## Виконано

| Задача | Результат |
|--------|-----------|
| Інвентар кодової бази | ✅ Перепис: 37 CRUD-сутностей, ~131 сервіс, 149 міграцій; ~18 функціональних областей; точки розширення醒 (mapApiV1Routes, Route::macro('crud') з рефлексією) |
| Дослідження 4 варіантів модульності | ✅ (a) nwidart/laravel-modules — відхилено; (b) власний реєстр + config/modules.php — **ОБРАНО**; (c) composer monorepo — відхилено; (d) feature-flags — можливий как Fase-0 |
| Архітектурний дизайн варіанту (b) | ✅ Структура app/Modules/{Name}/ (ModuleServiceProvider + module.php + опціональні папки); ModuleRegistry singleton; цикл enable/disable; ~10 одноразових змін ядра; Vue SPA через import.meta.glob + /bootstrap |
| Дослідження ліцензування | ✅ Ed25519 токени, гібрид офлайн-токен + heartbeat, enforcement через ModuleRegistry (ВІДКЛАДЕНО на майбутнє) |
| План фаз реалізації | ✅ Фази 0-6 від передумов (чистка debug-closures) до кінця: shortlinks (пілот) → CRUD/меню/lang → notifications → echeck → партнерські API ×5 → решта |

## Важливі рішення (ADR)

| Рішення | Чому | Альтернативи |
|---------|------|--------------|
| **Механізм модульності — власний легкий реєстр (варіант b)** | Лягає на наявну конвенцію routes(Router), повний контроль над CRUD/sidebar/lang-перекладами, поштучна міграція без крупої залежності від фреймворку | (a) nwidart — не розуміє CRUD/sidebar; (c) monorepo — важкий tooling; (d) feature-flags — тільки Fase-0 |
| **Ліцензування — відкладено** | Спочатку модульність як каркас; ModuleRegistry потім стане точкою enforcement для токенів/heartbeat | Реалізувати паралельно — дія зміщує пріоритети |
| **Модулі НЕ змінюють core-таблиці** | Поточна заклепа: moduli писали прямо в core (echeck_skip, send_survey, is_transfer_route). Нове правило: extension-таблиці 1:1 або нейтральні hook-поля | Дозволити модулям змінювати схему — істотно ускладнює plug-out |
| **transfers лишаються в ядрі** | Глибоке зчеплення з BookingService, впливає на дизайн черг і報告. Це не plug-out фіча | Виділити в модуль — розсипати BookingService переважно на сервіс-інтерфейси |
| **Меню/sidebar — серверне через /bootstrap** | Вимкнення модуля = зі сторони без перезбірки фронту (js/app.js не змінює) | СРА-сторонній Vue import — потребує перебудови при disable |
| **Моделі в первой итерации — НА МІСЦІ** | Ризик зміни неймспейсів (serialized jobs, activity_log.subject_type) перевищує вигоди від фізичної переорганізації | Перемістити в app/Modules/*/Entities — коштує пере-міграції + aliases |

## Проблеми й як вирішили

| Проблема | Рішення |
|----------|---------|
| DB-backed translation loader може глушити namespaced-ключі (lang/uk/module::field) | Перевірити першим при реалізації; можливо слід запуск простого FileServiceProvider |
| Зміна неймспейсів моделей ризикована (class_alias шим) | Лишити моделі в app/Entities на Fase-1; перемістити у модулі після stabilization + міграції |
| hasPermission === vs масив у sidebar — гейт мовчки не працює | Явна перевірка $user->hasPermissionTo(...) перед render-рендером меню |
| Vue SPA роутер без permission-guard | Додати вимогу в router.beforeEach() щоб чекувати права перед переходом (на Fase-3) |
| Перешкода plug-out: 6 модулів дописали колонки в core-таблиці (tickets, trips, route, orders) | Новий тип міграції: addModuleExtensionColumns (абстрактна, генерує на лету). Або скасувати всі та мігрувати в extension-таблиці |
